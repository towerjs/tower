Foundation is the lowest-level layer inside `@towerjs/tower`. It is not a publishable package — it provides the runtime infrastructure that all `@towerjs/*` modules depend on.

## createTowerApp

The primary way to create a Tower application. Pass an explicit `modules` array of callable module definitions:

```ts
import { gatehouse } from '@towerjs/gatehouse'
import { createTowerApp } from '@towerjs/tower/foundation'
import { vault } from '@towerjs/vault'

const app = await createTowerApp({
  modules: [
    vault({ connectionString: process.env.DATABASE_URL }),
    gatehouse({ provider: 'better-auth', credentials: { enabled: true } }),
  ],
})
```

Calling `createTower()` (no "App") adds config file resolution:

```ts
import { createTower } from '@towerjs/tower/foundation'

const app = await createTower() // resolves tower.config.ts automatically
```

In application code you never call `createTowerApp` directly — `tower.config.ts` with `defineTower({ modules: [vault(), gatehouse(...)] })` plus `getTowerApp()` / `initTower()` from `@towerjs/tower` wires everything. See `tower.config.ts` and `@towerjs/tower` core.

### TowerApp interface

```ts signature
interface TowerApp {
  config: TowerConfig
  container: ServiceContainer
  runtime: TowerRuntime
  shutdown(): Promise<void>
}
```

### Lifecycle

1. **Runtime detection** — platform is identified (Node, serverless, Edge)
2. **Service container** — created for this app instance
3. **Module factories** — each module config key maps to a registered factory
4. **Dependency validation** — modules are topologically sorted (circular deps throw)
5. **Registration** — each module's `register()` is called in dependency order
6. **Initialization** — each module's `initialize()` is called (async setup)
7. **App ready** — modules are accessible through their proxy APIs

## Runtime Detection

```ts
import { detectRuntime } from '@towerjs/tower/foundation'

const runtime = detectRuntime()
// → { name: 'node-server', isServerless: false }
// → { name: 'edge', isServerless: true }
// → { name: 'vercel-serverless', isServerless: true }
```

Detection checks environment variables: `VERCEL`, `AWS_LAMBDA_FUNCTION_NAME`, `AWS_EXECUTION_ENV`, `NETLIFY`, `CLOUDFLARE_WORKER`.

## Service Container

Per-app DI container:

```ts
import { ServiceContainer } from '@towerjs/tower/foundation'

const container = new ServiceContainer()

container.register('key', { ready: true })
container.has('key') // → boolean
container.get<{ ready: boolean }>('key') // → T
container.registerFactory('lazy', () => ({ ready: true }))
```

Each module registers its service under its bare name (e.g. `vault`, `gatehouse`). The `module.` prefix is used only for the internal lifecycle wrapper and is not part of the public API — resolve services by their bare name: `app.container.get('vault')`.

## Global Service Registry

For cross-module access after initialization:

```ts
import { getService, registerService } from '@towerjs/tower/foundation'

import { Pool } from 'pg'

registerService('database', new Pool())
const pool = getService<Pool>('database')
```

## Request Context

Tower uses AsyncLocalStorage to provide request-scoped context:

```ts
import { towerContext } from '@towerjs/tower/foundation'

const request = new Request('https://example.com')

await towerContext.run({ request, headers: request.headers }, async () => {
  // Gatehouse reads headers from context
})
```

In Edge environments, AsyncLocalStorage is replaced with a no-op provider.

## Config Resolution

```ts
import { resolveConfig } from '@towerjs/tower/foundation'

const config = await resolveConfig()
// Searches: providers → TOWER_CONFIG_PATH → filesystem walk
```
