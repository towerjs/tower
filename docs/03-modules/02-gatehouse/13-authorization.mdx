Authentication answers _who you are_; authorization answers _what you can do_. Gatehouse answers it with **policies**: plain application code that decides whether a user may perform an action on a resource.

## Policies

A policy is an object of action handlers. Each handler receives the authenticated Tower user and the resource — it never fetches the user itself, so policies unit-test without a request context:

```ts filename="src/policies/project.ts"
import { definePolicy, policies } from '@towerjs/gatehouse'

interface Project {
  id: string
  ownerId: string
}

export const projectPolicy = definePolicy<Project>({
  view: (user, project) => project.ownerId === user.id,
  update: (user, project) => project.ownerId === user.id,
})

policies.register('project', projectPolicy)
```

Register against a class (`policies.register(Project, projectPolicy)`) or a string key, as above.

## `can()` and `authorize()`

`can()` returns a boolean for the current user; `authorize()` throws instead — `AuthenticationError` when nobody is signed in, `AuthorizationError` when the policy denies:

```ts
import { gatehouse } from '@towerjs/gatehouse'

const project = { id: 'prj_123', ownerId: 'usr_123' }

if (await gatehouse.can(project, 'update')) {
  // ...
}

await gatehouse.authorize(project, 'update') // throws when denied
```

Both resolve the signed-in user from the request context, so they work inside `action()`, route handlers wrapped in `runWithRequest`, and the framework adapter's context. `can()` returns `false` for an unauthenticated visitor and throws only when no policy is registered for the resource.

## Permission checks

Role and permission checks — as opposed to resource policies — live on the per-request instance:

```ts
import { Gatehouse } from '@towerjs/gatehouse'

export async function GET(request: Request) {
  const gh = await Gatehouse.from(request)
  const user = await gh.requireUser()

  const allowed = await gh.can({ user, permission: 'project.update' })

  return Response.json({ allowed })
}
```

- `user` — the user to check (from `session()` or `requireUser()`)
- `permission` — a `string` or `string[]`; an array is **any-of** (checks that the user has at least one)
- `organizationId` — optional; when given, the check is scoped to the user's membership in that organization

## Where permissions come from

A user's permissions are the union of:

1. **User roles** — via `gatehouse.roles.assign(userId, role)`, with `gatehouse.role`-style permissions
2. **Organization roles** — the user's role inside the organization being checked, when `organizationId` is provided
3. **Ad-hoc grants** — plugin-defined permissions evaluated by the adapter

## Organization-scoped checks

Combine with [organizations](/docs/gatehouse/organizations): check the user's role _inside_ a specific organization.

```ts
import { Gatehouse } from '@towerjs/gatehouse'

export async function GET(request: Request) {
  const gh = await Gatehouse.from(request)
  const user = await gh.requireUser()

  const canEdit = await gh.can({
    user,
    permission: ['project.update', 'project.delete'],
    organizationId: 'org_123',
  })

  return Response.json({ canEdit })
}
```

Create custom roles with permission maps and assign them via invites or members:

```ts
import { gatehouse } from '@towerjs/gatehouse'

await gatehouse.organizations.roles.create({
  role: 'editor',
  permission: { project: ['update'] },
})

await gatehouse.organizations.invitations.create('org_123', {
  email: 'ada@example.com',
  role: 'editor',
})
```

Built-in organization roles: `owner`, `admin`, `member` — `owner` and `admin` imply all permissions in that organization.

## User roles (admin)

```ts
import { gatehouse } from '@towerjs/gatehouse'

const userId = 'usr_123'
const role = 'admin'

await gatehouse.admin.setRole({ userId, role }) // or any custom role
await gatehouse.roles.assign(userId, role) // same, module-level
```

Actions: `assignRole` (`userId`, `role`), `removeRole` (`userId`).

## Ownership checks

Role checks don't cover "is this _their_ record". Check ownership separately:

```ts
import { AuthorizationError, gatehouse } from '@towerjs/gatehouse'

const user = await gatehouse.requireUser()
const project = { id: 'prj_123', ownerId: 'usr_123' }

if (project.ownerId !== user.id) throw new AuthorizationError()
```

A policy is the place for this rule once more than one call site needs it — that is exactly what the `projectPolicy` above encodes.

## Enforcement points

| Where          | How                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------- |
| Server actions | `await gatehouse.authorize(resource, action)` on the first line                                 |
| Route handlers | `Gatehouse.from(request)` then `can()`                                                          |
| API keys       | `apiKeys.verify()` with a permission map                                                        |
| Pages          | Render what the session allows — access is gated by the proxy, so pages don't redirect for auth |

Fail closed: an unauthenticated visitor is denied rather than guessed at, and permission checks return `false` for unknown permissions — and when no `organizationId` is provided. Use `authorize()` where a denial should raise `AuthorizationError` (→ 403) instead of returning `false`.
