Tower is a **composable monolithic stack** for JavaScript and TypeScript applications. It provides the application-level infrastructure most products need — database access, authentication, and communication — as composable modules that sit alongside your web framework instead of replacing it.

Tower is not a web framework. It does not replace Next.js (or any other framework). Your framework remains the web layer; Tower supplies the application architecture underneath it — the modules, providers, and conventions that give you a consistent backend without assembling an ORM, an auth library, and an email provider by hand.

## The assembly problem

Without Tower, every application assembles the same stack: pick an ORM, pick an auth library, pick an email provider. Each is a solid choice on its own — but they don't know about each other. Authentication needs a database to store sessions and an email service for verification; email verification needs a database write and a delivery channel at the same time. Wiring those concerns together is where the real work lives.

With Tower, that stack comes pre-assembled. The modules are first-party, versioned and tested together, and share a single contract:

- **Register at import time** — modules declare themselves and their dependencies
- **Initialize on first use** — nothing runs at import, so Tower works in edge and SSR contexts
- **Expose a consistent API** — the same shapes, names, and patterns across modules

You configure providers instead of maintaining integrations.

## Why not assemble it yourself?

- **Choosing** — a dozen ORMs, a dozen auth libraries, a dozen email providers, each with its own mental model
- **Wiring** — cross-cutting flows (auth → sessions → email) require modules to know about each other
- **Versioning** — every dependency releases on its own cadence; breaking changes arrive independently
- **Testing** — integration boundaries are where bugs live, and testing glue is harder than testing modules
- **Consistency** — every developer reinvents the same auth flows, permission checks, and migration scripts

Tower trades the freedom to assemble for the speed and consistency of a well-factored whole. If your application later outgrows a single process, the module boundaries are your service boundaries — each module has a clean API surface and explicit dependencies.

## Modules

| Module        | Package              | Purpose                                                                          |
| ------------- | -------------------- | -------------------------------------------------------------------------------- |
| **Tower**     | `@towerjs/tower`     | Application core — Foundation + Blueprint as internal layers, runtime primitives |
| **Vault**     | `@towerjs/vault`     | Database ORM (Kysely), migrations, seeds, models                                 |
| **Gatehouse** | `@towerjs/gatehouse` | Authentication, sessions, organizations, API keys                                |
| **Courier**   | `@towerjs/courier`   | Email, SMS, push notifications                                                   |

Foundation and Blueprint are not publishable packages — they are internal layers of `@towerjs/tower` that provide its runtime infrastructure. See [Infrastructure](/docs/infrastructure).

## Tower today vs. Tower's direction

**Tower today (v0.2.0 core).** `@towerjs/tower` is the core (Foundation + Blueprint internal). Vault, Gatehouse, and Courier are optional `@towerjs/<module>` packages that depend on the core; the core never depends on modules. Next.js App Router is the supported framework. Scribe provides the `tower` CLI (`tower create`, `tower migrate`, `tower seed`). Vault uses the Neon HTTP dialect on Edge; Gatehouse Edge support is in progress.

**Tower's direction.** Future modules (job queues, storage, billing, search, observability) and additional framework integrations will follow the same contract: explicit `modules: [vault(), gatehouse(...)]` array, initialize lazily, expose a consistent API. The roadmap does not dictate today's decisions — the modules that exist now are the stable foundation.

## Framework Integration

`@towerjs/tower` has no framework dependencies. The core runtime adapts to any JavaScript environment — Node.js, serverless, or Edge — through automatic runtime detection.

Framework adapters live in each module's `frameworks/` directory. Currently only Next.js is supported:

- **Auth**: `getSession`, server actions, middleware proxy, API routes
- **Config**: Edge runtime bundling via `withTowerEdge`

## Installation

`@towerjs/tower` is the core, not a meta-package. Install the core plus the modules you need:

The `tower` CLI ships via `@towerjs/scribe` (installed with `towerjs` in generated apps as `tower dev`). For scaffolding, use `pnpm create tower`.

## When to Use Tower

- You want a batteries-included stack without microservice complexity
- You need production-grade database access, auth, and notifications out of the box
- You value vertical slice architecture and clean module boundaries
- You want to start monolithic and preserve the option to split later
- You're building on Next.js and want framework integration that Just Works
